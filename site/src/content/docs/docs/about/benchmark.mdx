This page gives every result of the benchmark I ran between Musonic Server and Navidrome, with the context you need to judge them. It is for anyone choosing a server, and for anyone who wants to check the numbers. How the test was run is on [Benchmark method](/docs/about/benchmark-method/); the scripts and the raw results are [on GitHub](https://github.com/DoodzDev/Musonic/tree/main/tools/benchmark).

<Aside type="note" title="Context of every number on this page">
**Musonic Server 1.0.1 against Navidrome 0.64.2**, measured on **2026-10-22**, on **one ARM virtual server** (Ampere Altra, 2 cores, 12 GB of memory), with **one library of 1,871 files** (7.0 GB, mostly MP3, 797 artists). Both servers ran without Docker, one at a time, from an empty data folder, **3 alternating passes**; each value is the **median of the 3 passes**.
</Aside>

## Key results

| What | Musonic | Navidrome | Ratio |
|---|---:|---:|---:|
| Scan of the whole library, from an empty database | **1.78 s** | 18.9 s | 10.6× |
| Memory at rest, 60 s after the scan | **19.5 MiB** | 100 MiB | 5.1× |
| List every artist (`getArtists`, 797 artists), median | **0.429 ms** | 52.7 ms | 122.9× |
| Search "love" (`search3`), median | **0.353 ms** | 29.4 ms | 83.4× |
| Slowest 5 % of the 14 everyday requests (p95), range | **0.361–3.56 ms** | 1.34–84.6 ms | 2.3× to 146.6× |
| Requests per second with 64 concurrent clients | **913** | 156 | 5.8× |
| Server CPU time per 1,000 requests | **0.58–0.60 s** | 11.0–12.1 s | 18.4× to 20.9× |
| First byte of a song transcoded for the first time | 42.0 ms | **33.5 ms** | Navidrome 1.3× |

Navidrome is ahead on **12 of the 113 measures** of the summary: the first transcoded byte, two size measures of covers, the throughput of an original file (by 6 %), the time to transcode a whole song (by 0.7 %), and the compressed size of 7 answers out of 14. They are all listed under [Where Navidrome is ahead](#where-navidrome-is-ahead).

The setup: the test script (`serverbench.py`, in Python) runs on the same machine (Ubuntu 24.04) and talks to one server at a time over HTTP on `127.0.0.1`, through the Subsonic API; it reads the server's memory and CPU time in `/proc`. Both servers read the same music folder (read only) and use the same ffmpeg n8.1 binary. The order of the passes: Musonic then Navidrome, Navidrome then Musonic, Musonic then Navidrome.

## How to read the tables

- **Each value is the median of the 3 passes.** The small numbers in brackets are the lowest and the highest of the 3 passes. No bracket means the 3 passes gave the same value at this precision.
- **Ratio** is always the better value divided by the worse one, so it is 1× or more. **Ahead** says which server has the better value; the better value is in bold.
- For times, memory, CPU time and sizes, lower is better. For requests per second and throughput, higher is better.
- Units: s (seconds), ms (milliseconds), MiB (1,048,576 bytes; Linux's `/proc` gives memory in units of 1,024 bytes, divided here by 1,024), KiB (1,024 bytes), MB (1,000,000 bytes, for the data folder and the throughput).
- A latency is measured by the client: from sending the request to receiving the whole answer, on a connection kept open, on the same machine. It includes the client's own time.

Several Navidrome routes answer faster in the two "after a like" series than in the back-to-back series above: the search "love" takes 29.4 ms back to back, 4.88 ms right after a like and 7.21 ms 300 ms after it. ## Where Navidrome is ahead

Every measure of the summary where Navidrome has the better value:

| Measure | Musonic | Navidrome | Navidrome ahead by |
|---|---:|---:|---:|
| First byte of a song transcoded for the first time | 42.0 ms | **33.5 ms** | 1.25× |
| Whole original file, throughput | 625 MB/s | **660 MB/s** | 1.06× |
| Whole song transcoded, first play | 2,779 ms | **2,760 ms** | 1.007× |
| 60 covers at 300 px, first request, total size | 1,091 KiB | **1,001 KiB** | 1.09× |
| 60 covers at 600 px, first request, total size | 3,701 KiB | **3,488 KiB** | 1.06× |
| Every artist (`getArtists`), compressed | 47.7 KiB | **30.0 KiB** | 1.59× |
| One artist (`getArtist`), compressed | 0.690 KiB | **0.490 KiB** | 1.41× |
| Search "mo" (`search3`), compressed | 8.88 KiB | **6.91 KiB** | 1.29× |
| 50 random songs (`getRandomSongs`), compressed | 13.2 KiB | **10.6 KiB** | 1.24× |
| Likes (`getStarred2`), compressed | 0.159 KiB | **0.134 KiB** | 1.19× |
| Search "love" (`search3`), compressed | 6.98 KiB | **5.95 KiB** | 1.17× |
| Genres (`getGenres`), compressed | 0.772 KiB | **0.690 KiB** | 1.12× |

What they mean:

- **First transcoded byte (33.5 against 42.0 ms).** This is the delay before a song starts when the server has to convert it and has never converted it before. Once converted, Musonic keeps the result on disk, and a second play starts in 1.25 ms against 1.72 ms. Since 1.0.1, when an app saves its play queue on the server (`savePlayQueue`), Musonic also converts the next song in the background before its turn; the benchmark does not save a queue, so this is not measured.
- **Compressed size of artists and searches.** In 1.0.1, Musonic's ids were 36-character UUIDs, which do not compress; Navidrome's are 22 characters. The list of every artist was 47.7 KiB against 30.0 KiB. Short ids came in Musonic Server 1.0.3 (see [What changed since](#what-changed-since)).
- **Covers at the very first request** are 6 to 9 % heavier with Musonic, then 7 to 9 % lighter 10 s later, once the background version replaced them.
- **Throughput of an original file** (625 against 660 MB/s) and the **time to transcode a whole song** (2,779 against 2,760 ms) differ by 6 % and 0.7 %; the ranges of the passes overlap for the throughput (616–660 against 631–720 MB/s).

## About the single average number

The previous version of this site showed **"6.9× on average, over 36 measures"**. Here is where it comes from, and why this page does not use one number as its headline.

- It is the **geometric mean** of 36 ratios, each written as "how many times better Musonic is" (Navidrome ÷ Musonic for times, memory and sizes; Musonic ÷ Navidrome for throughput), so a measure where Navidrome is ahead counts as a value below 1. The geometric mean is the n-th root of the product of the n ratios, the usual way to average speed-ups.
- The 36 measures were: the 9 of scan, memory, startup and disk; the 14 median latencies; the 4 throughputs and the CPU time per 1,000 requests; and 8 of covers and playback (first cover at 300 and 600 px, cover asked again at 300 px, first byte of an original file, first transcoded byte, transcoded second play, `ping` with a token, throughput of an original file).
- Recomputed from the raw results with unrounded medians, it is **6.95**. The 6.9 shown before came from rounded values (for example 11.7 s ÷ 0.6 s for the CPU time).
- The same mean over **all 113 measures** of the summary (with the p95, the "after a like" series, the latency under load and every size) is **5.14**.
- An average depends on which measures you put in it, and it hides the measures where Navidrome is ahead. Read the tables above for what matters to you.

## What this benchmark does NOT show

- **A large library.** 1,871 files, 7.0 GB, 797 artists, about 1,000 albums: a small library. Nothing here says how either server behaves with 30,000 or 100,000 songs. That test is planned (see [Benchmark method](/docs/about/benchmark-method/#planned)).
- **Other hardware.** One ARM virtual server with 2 cores and 12 GB of memory. Not a Raspberry Pi, not an x86 machine, not a NAS, not a hard disk.
- **A quiet machine.** Other services were running on the same server during the run, for both servers alike.
- **A separate load generator.** The test client runs on the same 2 cores as the server. It caps Musonic at about 900 requests per second, and its own time is inside every latency: Musonic's sub-millisecond medians are close to the floor of the measure (`ping` takes 0.270 ms).
- **Tuned settings.** Navidrome ran with its default settings, except that its scheduled scan, external services, Last.fm and usage statistics were turned off. Musonic ran with its defaults, except that its online catalogue, previews, imports and update check were turned off. Neither server was tuned for this test.
- **Several dates or machines.** One run, on one evening, on one machine. The 3 passes show how stable the numbers are on that machine, not on another.
- **The apps.** This is a server test. It says nothing about the Musonic apps, the Subsonic apps or the network between them and the server.
- **Features.** It compares speed and resources on the same Subsonic requests, not what each server can do.
- **Rescans.** Only the first full scan of an empty database was measured, not a rescan after a few files changed.
- **Today's versions.** See below.

## What changed since

The measures are for **Musonic Server 1.0.1** and **Navidrome 0.64.2**. Both have changed since; the benchmark has not been run again.

- **Short ids** (Musonic Server 1.0.3): songs, albums, artists, folders and playlists now have 11-character ids instead of 36. According to the 1.0.3 changelog, this makes the list of artists 42 % lighter, 500 albums 24 % and a search about 20 %. These are Musonic-only figures, not measured against Navidrome: **the compressed sizes on this page are those of 1.0.1**, and today's Musonic answers are smaller.
- **`/health`** (Musonic Server 1.0.3) no longer reports the scan. The script now falls back to the Subsonic `getScanStatus` route, so it works with current versions (see the [script's README](https://github.com/DoodzDev/Musonic/tree/main/tools/benchmark)).
- The current version of Musonic Server is 1.2.1. Navidrome has its own releases after 0.64.2. Neither has been measured since 2026-10-22.
