This page lists everything Musonic Server answers over HTTP, for developers who write a client, a script or an integration. It is taken from the server's source code (`apps/server/src`), version 1.2.1.

**What you need**

- A running Musonic Server and its address (in the examples: `https://music.example.com`).
- An account on it. For scripts, create an API key for the device (see [Authentication](#authentication)).

Musonic Server exposes three things:

| Base path | What it is | Format |
|---|---|---|
| `/rest/<endpoint>` | The Subsonic / OpenSubsonic API, used by Musonic and by any Subsonic client | XML by default, JSON with `f=json` |
| `/v1/...` | The native API of Musonic: accounts, sign-in, real-time events, administration | JSON |
| `/health` | Liveness check, without sign-in | JSON |

It also serves two web apps: the administration console at the server's address (`/`, and any path that is not an API), and Musonic Web at `/app/` once it is installed from the console.

## Subsonic and OpenSubsonic API

### Version and answer format

- Subsonic API version advertised: **1.16.1**.
- Every answer carries `status` (`ok` or `failed`), `version` (`1.16.1`), `type` (`musonic`), `serverVersion` (the server's version) and `openSubsonic: true`.
- Routes answer at `/rest/<endpoint>` and `/rest/<endpoint>.view`, with any HTTP method.
- Parameters are read from the query string **and** from a form body (`application/x-www-form-urlencoded`, the OpenSubsonic `formPost` extension). Repeated keys are kept (`id=a&id=b`).
- Answers are XML by default, JSON with `f=json`, JSONP with `f=jsonp&callback=<name>` (letters, digits, `_` and `.`, 64 characters at most; otherwise JSON).
- Errors use the Subsonic codes: `0` generic, `10` missing parameter, `40` wrong credentials, `41` token sign-in not available, `42` mechanism not supported, `43` conflicting mechanisms, `44` invalid API key, `50` not authorized, `70` not found.

### Authentication

Every route except `getOpenSubsonicExtensions` needs credentials. Three methods are accepted:

| Method | Parameters | Notes |
|---|---|---|
| API key (OpenSubsonic `apiKeyAuthentication`) | `apiKey=<key>` | Recommended. Keys start with `msk_`. Must not be combined with `u`, `p`, `t` or `s` (error `43`). |
| Password | `u=<user>&p=<password>` or `p=enc:<hex>` | The password in clear or hex-encoded after `enc:`. Use it only over HTTPS. |
| Token and salt (classic Subsonic) | `u=<user>&t=<md5(password + salt)>&s=<salt>` | Works only while the server setting `legacy_auth` is on (the default). When it is off, the server answers error `41` and asks for `apiKey`. |

- `<key>`: an API key created in the app, in the console, or with `POST /v1/me/api-keys` (shown once).
- `<user>`, `<password>`: the account's username and password.
- `<salt>`: a random string you choose for each request; `<md5(password + salt)>` is the MD5 hash, in hex, of the password followed by that salt.

```sh
curl "https://music.example.com/rest/ping?apiKey=<key>&c=my-script&f=json"
```

<Aside type="note">
After 10 different wrong passwords for one account from one address, that address is refused for that account for 15 minutes, even with the right password. Retrying the same wrong password does not count again. The address is taken from `CF-Connecting-IP`, else `X-Forwarded-For`, else the connection.
</Aside>

A suspended account gets error `50` with the message "This account is suspended".

### OpenSubsonic extensions

`getOpenSubsonicExtensions` answers without credentials:

| Extension | Versions | Meaning |
|---|---|---|
| `apiKeyAuthentication` | 1 | `apiKey` parameter, `tokenInfo` |
| `formPost` | 1 | Parameters in a form body |
| `indexBasedQueue` | 1 | `savePlayQueueByIndex`, `getPlayQueueByIndex` |
| `musonicServer` | 1, 2, 3, 4 | The server is Musonic Server. 2: the one-request routes `getMusonicLibrary`, `getMusonicHome`, `getMusonicHomeMore`. 3: short ids (old UUIDs still accepted). 4: podcasts (`searchPodcasts`, `savePodcastPosition`, listening positions). |

A client can check for `musonicServer` (or call [`GET /v1/info`](#server-and-sign-in)) to use Musonic's extras, and keep working with any other Subsonic server.

### Not implemented

Bookmarks (`getBookmarks`, `createBookmark`, `deleteBookmark`), shares, jukebox (`jukeboxControl`), videos, chat, avatars (`getAvatar`), `updateUser`, `search` (Subsonic 1.x), podcast episode download and deletion (`downloadPodcastEpisode`, `deletePodcastEpisode`), internet radio management.

### Streaming

`stream` sends the file as it is, with HTTP ranges so players can seek, unless the client asks otherwise:

| Parameter | Effect |
|---|---|
| `format=raw` | Never transcode. |
| `format=mp3`, `opus`, `aac` (or `m4a`), `ogg` | Transcode to that format when the file is in another one. |
| `maxBitRate=<kbit/s>` | Transcode when the file is above it (capped at 320). |
| `timeOffset=<seconds>` | Start a transcoded stream later. |

- When only the bit rate is too high, the format used is the server setting `transcode_format` (`mp3` by default; `opus` and `aac` possible).
- Default bit rates when none is asked: 192 kbit/s for MP3, 128 for Opus, 256 for AAC. A smaller file is never "upscaled".
- The account's bit-rate limit and the server's `max_bit_rate` win over what the client asks: the lowest applies.
- Transcoded songs are kept on disk (`transcode_cache_mb`, 500 MB by default), so a song played again or seeked starts at once. The next song of the saved queue is prepared in the background.
- Without ffmpeg, files are sent as they are.
- A track without a file is streamed from the first audio provider that has it, through a shared disk cache split in 1 MiB segments, with ranges too.

## Native API (`/v1`)

JSON in and out. Errors are `{"error": "<message>"}` with an HTTP status (`400`, `401` "sign in required", `403` "administrators only", `404`, `409`, `429`, `500`).

### Authentication

`Authorization: Bearer <token>`, where `<token>` is either:

- a **session token**, returned by `POST /v1/auth/login` or `POST /v1/setup`. It lasts 30 days without use, and each use extends it;
- an **API key** (`msk_…`).

```sh
curl -X POST https://music.example.com/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"<user>","password":"<password>","client":"my-script"}'
# {"token":"…","user":{…}}

curl https://music.example.com/v1/me -H "Authorization: Bearer <token>"
```

`POST /v1/auth/login` also accepts `token` and `salt` (the Subsonic `md5(password + salt)` and its salt) instead of `password`, under the same `legacy_auth` setting. `client` is the name shown in the activity journal. It returns `429` when the address is locked out (see above) and `403` for a suspended account.

A few routes cannot send a header (a WebSocket, an `<img>`, an `<audio>`): they take the token as `?token=` instead, as noted below.

## Real-time events (`/v1/events`)

`GET /v1/events` is a **WebSocket**. Every device of an account learns at once what changed for that account, whichever client made the change (Subsonic clients included).

- Sign-in: `Authorization: Bearer <token>`, or `?token=<token>` (browsers cannot set headers on a WebSocket).
- Device id: `?device=<id>` or the `X-Musonic-Device` header, chosen by the client (64 characters at most). Send the same header or `device` parameter on your other requests: events caused by your device carry `by: <id>`, so it can ignore its own echo.
- Events are not stored. A device that connects again reloads what it shows.

```js
const ws = new WebSocket('wss://music.example.com/v1/events?token=<token>&device=<id>');
ws.onmessage = (e) => console.log(JSON.parse(e.data));
```

Each message is a JSON object `{type, at, by?, …}`: `at` in Unix seconds, `by` the device that made the change when it said so.

| `type` | Fields | When |
|---|---|---|
| `hello` | `user {id, username}`, `device`, `features` | First message of a connection. |
| `likes` | `items [{kind, id, starred}]` (`kind`: `track`, `album`, `artist`) | Likes changed. |
| `rating` | `kind`, `id`, `rating` | A rating changed. |
| `playlist` | `id`, `action` (`created`, `updated`, `deleted`) | A playlist changed. |
| `play` | `ids` | Plays were counted. |
| `queue` | — | The saved play queue changed. |
| `import` | `id`, `state` (`done`, `failed`), `path` | An online track was imported into the library, or failed. |
| `playlistImport` | `id`, `state` (`running`, `done`, `failed`), `done`, `total`, `playlist` | A playlist import went on. |
| `devices` | `devices` | Musonic Connect: the account's devices online changed. |
| `player` | `player`, `now` | Musonic Connect: what a device plays; `now` is the server time in ms. |
| `command` | `command` | Musonic Connect: a remote command for the device `command.to`. |
| `commandFailed` | `command`, `reason` (`offline`, `notAllowed`) | A command did not reach its device. |
| `settings` | `connectSync` | The account's settings changed. |
| `ping` | — | Keep-alive, every 30 seconds. |
| `resync` | — | The device was too slow and missed events: reload what is shown. |

### Musonic Connect messages

Musonic Connect (beta) uses the same WebSocket in both directions. The server plays nothing: it keeps the last state of each device in memory, dates it with its own clock and relays it. A device sends:

| `type` | Content |
|---|---|
| `register` | The device: `name` (64 characters at most), `kind` (`phone`, `web`, `desktop`, `car`, `speaker`…), `canPlay`, `volume`, `alone`. The server answers with what the account's devices play. |
| `player` | What it plays: `track`, `title`, `artist`, `album`, `coverArt`, `duration` (s), `playing`, `position` (ms), `queue`, `shuffle` (`off`, `on`, `magic`), `repeat` (`none`, `all`, `one`), `volume` (0–100). Ignored until the device registered. |
| `command` | `to` (a device id), `action` (`play`, `pause`, `toggle`, `next`, `previous`, `seek`, `volume`, `playItem`, `transfer`), `params`, and `user` for an administrator acting on another account. |

The server sets `player.device`, `player.positionAt` (server time of `position`, ms) and `command.from`. The last state is also saved per account, for `GET /v1/me/player`. Anything else sent on the socket is ignored.

## Caching and compression

- Text answers (JSON, XML, JavaScript, HTML) over 1 KB are compressed with gzip for clients that send `Accept-Encoding: gzip`. Audio and pictures are sent as they are.
- Read-only Subsonic answers are kept in memory, per account, until the database changes: `getArtists`, `getIndexes`, `getMusicFolders`, `getGenres`, `getStarred`, `getStarred2`, `getPlaylists`, `getSongsByGenre`, `getMusonicLibrary`; `getAlbum`, `getArtist`, `getSong`, `getPlaylist`, `getMusicDirectory` for library ids; `getAlbumList` and `getAlbumList2` except `type=random`; `search2` and `search3` when the online catalog is off.
- Those answers carry a weak `ETag`, `Cache-Control: private, no-cache` and `Vary: accept-encoding`. Send the `ETag` back in `If-None-Match`: the server answers `304 Not Modified` while nothing changed.
- After a write (a like, a play), the most requested answers are rebuilt in the background, so the next screen finds them ready.
- CORS is open to any origin, without cookies. Allowed request headers: `Authorization`, `Content-Type`, `Range`, `If-None-Match`. Exposed: `Content-Range`, `Content-Length`, `Accept-Ranges`, `ETag`.
- Every answer carries `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'` and `Referrer-Policy: no-referrer`.

## Ids

| Item | Format | Example |
|---|---|---|
| Tracks, albums, artists, folders, playlists | Short id: 64 bits in base 62, always 11 characters | `3kQ9xZ0aB7c` |
| Online catalog items | `dz-track-<n>`, `dz-album-<n>`, `dz-artist-<n>` | `dz-track-3135556` |
| Podcast shows, episodes | `pc-…`, `pe-…` | |
| Cover ids | `pl-<playlist id>` (playlist picture), `ar-<artist id>` (artist picture) | |
| Accounts, keys, links | UUID | |

- A track keeps its id across rescans, moves and imports: an online track that gets a file keeps the id it had.
- Older ids (UUIDs from before server 1.0.3, or 22-character ids imported from Navidrome) are still accepted in `id`, `albumId`, `artistId`, `songId`, `songIdToAdd`, `playlistId`, `current` and `song`, and turned into the current short id.

## TypeScript types

The JSON types of the native API and of the events are written in Rust and generated as TypeScript with `ts-rs`: `cargo test` in `apps/server` writes them to `packages/core/src/server/generated` (for example `ServerInfo`, `EventMessage`, `Event`, `ConnectDevice`, `Player`, `Command`). The server's CI fails when the committed types are out of date. TypeScript clients import them from `@musonic/core`.
